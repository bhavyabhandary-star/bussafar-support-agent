## How to re-run

From the project root, with `GOOGLE_API_KEY` (and `APP_PASSCODE`) in `.env`:

```bash
pip install -r requirements-full.txt
python -m pytest -q                      # unit + UI tests (offline, no API calls)
RUN_LIVE_TESTS=1 python -m pytest -q tests/test_live_agent.py   # live Gemini checks (optional)
python tests/qa/run_qa.py                # full QA plan, live Gemini, paced at 12 calls/min
python tests/qa/run_qa.py --only POL,DEL # re-run some modules (rewrites the report with only those rows)
python tests/qa/run_qa.py --offline      # no API calls; model-dependent cases show Blocked
```

A full live run makes about 95 Gemini calls (roughly 10 minutes on the free tier; the free daily quota is about 500). Test data is the 16 fictional bookings in `data/bookings.csv` (12 from the data sheet plus 4 demo rows for Pending, Failed, Refunded and No-Show); phone digits are shown as `****` in every report. Conversation quality, booking status and support ticket cases run in code, so they pass or fail even offline. UI-014 (mobile) is checked with headless Chromium at 375×812 and read from `tests/qa/ui_mobile_result.json`.

## Clarifications (current behaviour, not new policy)

- **Refund processing timeline when a bus is more than 3 hours late:** The help docs only say the traveller can cancel for a full refund. Sahil quotes that and does not state a processing time for this case. It does not borrow the 5 to 7 working day or 3 working day timelines unless the customer asks about refunds generally.
- **Support ticket SLA and human-support contact mechanism:** Not in the help docs. Following the project brief, Sahil says 'A person from our support team will reply within 24 hours' after creating a ticket. Tickets are saved to tickets.csv with a status (Pending, In progress, Done) and every change is logged in tickets_history.csv. Both reset on restart when hosted on Render's free plan. No phone number or email is given.
- **Is the ₹2,000 rule the requested refund or the booking amount?:** Implemented as the requested refund amount named in the message (₹/Rs/INR/rupees). Above ₹2,000 creates a refund_dispute ticket in code. Exactly ₹2,000 does not escalate on amount alone (POL-010). The booking amount is not used, and none of the 16 bookings exceeds ₹2,000.
- **Date change when no seats are available:** Not in the help docs. Sahil states the documented rule (once, up to 24 hours before departure, ₹100 plus fare difference) and does not invent an availability rule. If pressed, it gives the fallback and offers a person.
- **ESC-010 / CONV-006 duplicate escalation:** One ticket per chat, enforced in code. Any later hand-off (lost item, bus no-show, person requested, refund above ₹2,000) returns the open ticket's ID and says no new ticket was created. Two exceptions: a safety problem always gets its own high-priority ticket, and once staff mark the ticket Done a new one can be raised.
- **Who can change a ticket status?:** Only staff: the sidebar 'Staff: update a ticket' form or `python manage_tickets.py set TKT-1001 Done note`. Customers can only check a status, by ticket ID, in chat or the sidebar. Sahil shows the status, its meaning and the latest staff note, never the original message or booking details.
- **'Status of my ticket' without the word 'support':** Read as a bus ticket (booking), so Sahil asks for the PNR and last 4 phone digits. 'Support ticket', 'complaint ticket' or a TKT- ID is read as a support ticket.
